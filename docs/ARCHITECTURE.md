## 二、核心架构亮点

### 2.1 Event Bus - 发布订阅事件总线

#### 设计理念

Event Bus 是系统的核心通信枢纽，采用**发布-订阅模式**实现模块间完全解耦。

#### 架构特点

```
┌─────────────────────────────────────────────────────────────────┐
│                        Event Bus                                │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │                    事件队列 (Queue)                       │   │
│  │  ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐     │   │
│  │  │ E1  │ │ E2  │ │ E3  │ │ E4  │ │ E5  │ │ ... │     │   │
│  │  └─────┘ └─────┘ └─────┘ └─────┘ └─────┘ └─────┘     │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │                  订阅者管理 (Subscribers)                  │   │
│  │  ┌──────────────┬──────────────┬──────────────┐         │   │
│  │  │ 事件类型      │  处理函数     │  用户数据     │         │   │
│  │  ├──────────────┼──────────────┼──────────────┤         │   │
│  │  │ WIFI_CONNECTED│ on_wifi()   │  NULL        │         │   │
│  │  │ SENSOR_DATA  │ on_sensor() │  &sensor_ctx │         │   │
│  │  │ LORA_RX      │ on_lora()   │  &lora_ctx   │         │   │
│  │  └──────────────┴──────────────┴──────────────┘         │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │              事件处理任务 (Event Handler Task)             │   │
│  │          独立任务，异步处理，不阻塞发布者                    │   │
│  └─────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────┘

发布者 (Publisher)                    订阅者 (Subscriber)
      │                                      │
      │  event_bus_publish(EVENT_TYPE, &data) │
      ├─────────────────────────────────────►│
      │                                      │
      │         event_bus_subscribe()        │
      │◄─────────────────────────────────────┤
      │                                      │
      │    [异步] handler(event, user_data)   │
      └─────────────────────────────────────►│
```

#### 事件类型编码规则

```c
// 事件类型格式: (MODULE_ID << 16) | EVENT_ID
// 高16位: 模块ID (0x0001-0x000A)
// 低16位: 事件ID (0x0001-0xFFFF)

#define MODULE_ID_SYSTEM    0x0001
#define MODULE_ID_WIFI      0x0002
#define MODULE_ID_SENSOR    0x0003
#define MODULE_ID_TOUCH     0x0004
#define MODULE_ID_LORA      0x0005
#define MODULE_ID_AUDIO     0x0007
#define MODULE_ID_STORAGE   0x0008
#define MODULE_ID_DISPLAY   0x0009

// 示例
EVENT_SENSOR_TEMP_HUMIDITY = (MODULE_ID_SENSOR << 16) | 0x0001
EVENT_LORA_DATA_RECEIVED   = (MODULE_ID_LORA << 16) | 0x0001
```

#### 核心API

```c
// 初始化
event_bus_err_t event_bus_init(void);

// 发布事件 (类型安全宏)
EVENT_BUS_PUBLISH(EVENT_TYPE, &data);      // 带数据
EVENT_BUS_PUBLISH_EMPTY(EVENT_TYPE);       // 无数据

// 订阅事件
event_subscription_t* sub = event_bus_subscribe(
    EVENT_WIFI_CONNECTED,   // 事件类型
    on_wifi_connected,      // 处理函数
    NULL                    // 用户数据
);

// 取消订阅
event_bus_unsubscribe(sub);
```

#### 技术优势

| 特性 | 说明 |
|------|------|
| **完全解耦** | 发布者和订阅者互不知道对方存在 |
| **异步处理** | 事件入队后立即返回，不阻塞发布者 |
| **类型安全** | 编译时检查事件类型和数据结构 |
| **线程安全** | 内部使用互斥锁保护共享数据 |
| **内存高效** | 固定大小队列，柔性数组存储事件数据 |
| **可观测性** | 内置统计信息：发布数、处理数、丢弃数 |

### 2.2 Tasker - 三级优先级任务调度器

#### 设计理念

Tasker 采用**三级优先级队列**设计，根据任务耗时自动分配到不同队列，确保系统响应性。

#### 架构特点

```
┌─────────────────────────────────────────────────────────────────┐
│                        Tasker 调度器                            │
│                                                                 │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │                任务提交 (tasker_enqueue)                  │   │
│  │                     ┌─────────┐                          │   │
│  │                     │ task_node│                         │   │
│  │                     └────┬────┘                          │   │
│  │                          │                               │   │
│  │              ┌───────────┼───────────┐                   │   │
│  │              ▼           ▼           ▼                   │   │
│  │  ┌───────────────┐ ┌───────────┐ ┌───────────────┐      │   │
│  │  │ Little Queue  │ │Middle Queue│ │  Lots Queue   │      │   │
│  │  │  (快速任务)    │ │ (普通任务) │ │  (重量任务)    │      │   │
│  │  │  超时: 50ms   │ │ 超时: 1000ms│ │ 超时: 10000ms │      │   │
│  │  │  栈: 3KB     │ │ 栈: 4KB   │ │  栈: 8KB      │      │   │
│  │  │  队列: 8     │ │ 队列: 8   │ │  队列: 8      │      │   │
│  │  └───────┬───────┘ └─────┬─────┘ └───────┬───────┘      │   │
│  │          │               │               │               │   │
│  │          ▼               ▼               ▼               │   │
│  │  ┌───────────────────────────────────────────────────┐   │   │
│  │  │              调度器 (Dispatcher)                    │   │   │
│  │  │     从队列取出任务，分配给工作者线程执行              │   │   │
│  │  └───────────────────────────────────────────────────┘   │   │
│  │                          │                               │   │
│  │          ┌───────────────┼───────────────┐               │   │
│  │          ▼               ▼               ▼               │   │
│  │  ┌───────────┐   ┌───────────┐   ┌───────────┐          │   │
│  │  │ Worker 1  │   │ Worker 2  │   │ Worker N  │          │   │
│  │  └───────────┘   └───────────┘   └───────────┘          │   │
│  └─────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────┘
```

#### 任务节点结构

```c
struct task_node {
    int done;           // 完成标志
    int cancel;         // 取消标志
    int timeout;        // 超时时间 (ms)
    int is_timeout;     // 是否超时
    int period;         // 周期 (ms, 0表示一次性)
    int run_cnt;        // 运行次数 (-1表示无限)
    enum task_priority pri;      // 优先级
    enum task_time_cost_level level; // 耗时级别
    task_fn fn;         // 任务函数
    uint64_t inject_time; // 注入时间
    char name[32];      // 任务名称
    void* ctx;          // 用户上下文
};
```

#### 核心API

```c
// 初始化任务节点 (三种优先级)
tasker_task_init_li(&node, period, run_cnt, name, fn, ctx);  // 快速任务
tasker_task_init_mi(&node, period, run_cnt, name, fn, ctx);  // 普通任务
tasker_task_init_lo(&node, timeout, period, run_cnt, name, fn, ctx); // 重量任务

// 提交任务到调度器
tasker_enqueue(&node);

// 取消任务
tasker_cancel_by_node(&node);
tasker_cancel_by_name("task_name");
```

#### 任务分类策略

| 级别 | 超时 | 栈大小 | 适用场景 |
|------|------|--------|----------|
| **Little** | 50ms | 3KB | GPIO控制、状态查询、简单计算 |
| **Middle** | 1000ms | 4KB | 传感器读取、UI更新、网络请求 |
| **Lots** | 10000ms | 8KB | 文件操作、OTA升级、大数据处理 |

#### 技术优势

| 特性 | 说明 |
|------|------|
| **自动分级** | 根据任务耗时自动选择队列 |
| **超时保护** | 防止单个任务阻塞整个系统 |
| **周期执行** | 支持一次性或周期性任务 |
| **动态取消** | 运行时可取消已提交的任务 |
| **资源隔离** | 不同级别任务使用独立栈空间 |

### 2.3 Device Tree - JSON设备树配置系统

#### 设计理念

借鉴Linux设备树思想，使用**JSON文件描述硬件配置**，实现硬件参数与代码完全分离。

#### 架构特点

```
┌─────────────────────────────────────────────────────────────────┐
│                    Device Tree 设备树系统                        │
│                                                                 │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │                 JSON 配置文件层                           │   │
│  │  ┌───────────┐ ┌───────────┐ ┌───────────┐ ┌─────────┐ │   │
│  │  │ spi.json  │ │ i2c.json  │ │ i2s.json  │ │uart.json│ │   │
│  │  └───────────┘ └───────────┘ └───────────┘ └─────────┘ │   │
│  │  ┌───────────┐ ┌───────────┐ ┌───────────┐ ┌─────────┐ │   │
│  │  │lora.json  │ │audio.json │ │display.json│ │ ...    │ │   │
│  │  └───────────┘ └───────────┘ └───────────┘ └─────────┘ │   │
│  └─────────────────────────────────────────────────────────┘   │
│                           │                                     │
│                           ▼                                     │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │                 解析器层 (dtree)                          │   │
│  │  ┌───────────────────────────────────────────────────┐  │   │
│  │  │  JSON Parser → 内存树结构 → 属性查询API            │  │   │
│  │  └───────────────────────────────────────────────────┘  │   │
│  └─────────────────────────────────────────────────────────┘   │
│                           │                                     │
│                           ▼                                     │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │                 驱动层读取配置                            │   │
│  │                                                         │   │
│  │  // 示例: SPI驱动从设备树读取配置                         │   │
│  │  spi_drv_config_t config;                               │   │
│  │  DTREE_INT("spi.bus", "sclk_pin", &config.sclk_pin);   │   │
│  │  DTREE_INT("spi.bus", "miso_pin", &config.miso_pin);   │   │
│  │  DTREE_INT("spi.bus", "mosi_pin", &config.mosi_pin);   │   │
│  │  DTREE_INT("spi.bus", "max_freq_mhz", &config.freq);   │   │
│  └─────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────┘
```

#### 核心API

```c
// 初始化设备树
dtree_init();

// 获取节点
dtree_node_t* node = dtree_get_node("spi.lcd_display");

// 读取属性

dtree_err_t ret = DTREE_INT("spi.lcd_display", "cs_pin", &pin);

// 检查节点/属性是否存在
bool exists = dtree_has_node("i2c.sensor");
bool has_prop = dtree_has_property(node, "address");
```

#### 技术优势

| 特性 | 说明 |
|------|------|
| **配置与代码分离** | 修改硬件配置无需改代码 |

| **类型安全** | 编译时检查属性类型 |
| **错误处理** | 完整的错误码体系 |
| **易于扩展** | 添加新设备只需添加JSON配置 |

### 2.4 LVGL - 六层UI架构

#### 设计理念

采用**六层分层架构**，实现UI与业务逻辑完全解耦，提高代码可维护性和可测试性。

#### 架构特点

```

│   用户看到   │◄───│  UI控件      │◄───│  Presenter   │◄───│   后端返回   │
│  (界面更新)   │    │  (更新显示)   │    │  (更新数据)   │    │  (数据/结果)  │
└──────────────┘    └──────────────┘    └──────────────┘    └──────────────┘
```

#### 各层职责详解

| 层级 | 职责 | 原则 |
|------|------|------|
| **UI层** | 纯视觉和交互实现 | 只关心控件外观，不关心业务 |
| **Widgets层** | 组合控件成最小操作单元 | 对话框、输入框等可复用组件 |
| **Pages层** | 组合控件和窗口成完整页面 | 每个页面对应一个功能模块 |
| **Navigator层** | 管理页面生命周期 | 页面栈、切换动画、父子关系 |
| **Presenters层** | 实现具体业务逻辑 | 回调函数、数据处理、UI更新 |
| **Bridge层** | 对接后端和硬件 | 抽象硬件接口，便于测试 |

#### 技术优势

| 特性 | 说明 |
|------|------|
| **分层解耦** | UI与业务逻辑完全分离 |
| **可测试性** | Bridge层可Mock，便于单元测试 |
| **可复用性** | Widgets可在多个页面复用 |
| **易于维护** | 修改UI不影响业务，反之亦然 |
| **团队协作** | 不同开发者可并行开发不同层 |

### 2.5 Holder - 全局硬件模块注册表管理器

#### 设计理念

Holder模块是系统的**硬件模块管理中心**，采用**注册表模式**统一管理所有硬件模块的注册、初始化和状态监控。主要解决硬件模块故障导致系统崩溃的问题，提高系统健壮性。

#### 架构特点

```
┌─────────────────────────────────────────────────────────────────┐
│                      Holder 模块管理器                          │
│                                                                 │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │                  模块注册表 (Registry)                    │   │
│  │  ┌──────────────┬──────────────┬──────────────┐         │   │
│  │  │ 模块名称      │  初始化函数   │  状态信息     │         │   │
│  │  ├──────────────┼──────────────┼──────────────┤         │   │
│  │  │ st7789       │ st7789_init()│ READY        │         │   │
│  │  │ w25q128      │ w25q128_init│ ERROR        │         │   │
│  │  │ lora         │ lora_init() │ READY        │         │   │
│  │  │ aht30        │ aht30_init()│ INITIALIZING │         │   │
│  │  └──────────────┴──────────────┴──────────────┘         │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │                  状态监控 (Status Monitor)                │   │
│  │  • 模块状态跟踪 (UNKNOWN/REGISTERED/READY/ERROR)         │   │
│  │  • 错误计数统计                                          │   │
│  │  • 初始化耗时记录                                        │   │
│  │  • 必需/可选模块区分                                     │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │              初始化管理 (Initialization Manager)          │   │
│  │  • 统一初始化流程                                        │   │
│  │  • 故障隔离机制                                          │   │
│  │  • 依赖顺序管理                                          │   │
│  │  • 降级运行支持                                          │   │
│  └─────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────┘
```

#### 核心功能

| 功能 | 说明 | 优势 |
|------|------|------|
| **模块注册** | 统一注册硬件模块及其初始化函数 | 集中管理，易于维护 |
| **状态跟踪** | 实时监控模块状态和错误信息 | 快速定位问题 |
| **故障隔离** | 单个模块故障不影响其他模块 | 提高系统稳定性 |
| **错误统计** | 记录错误次数和最后错误信息 | 便于调试分析 |
| **初始化管理** | 统一初始化流程和顺序 | 避免依赖冲突 |
| **降级运行** | 非必需模块失败时系统继续运行 | 保证基本功能 |

#### 核心API

```c
// 初始化holder模块
holder_err_t holder_init(void);

// 注册模块到holder
holder_err_t holder_register_module(const char* name, 
                                   holder_module_init_fn init_fn,
                                   bool required,
                                   void* user_data);

// 初始化所有已注册模块
holder_err_t holder_init_all(bool stop_on_required_error);

// 检查模块是否就绪
bool holder_is_module_ready(const char* name);

// 获取模块状态
holder_module_state_t holder_get_module_state(const char* name);

// 打印所有模块状态（调试用）
void holder_print_status(void);
```

#### 模块状态机

```
UNKNOWN → REGISTERED → INITIALIZING → READY
                    ↘               ↗
                     → ERROR →
```

| 状态 | 说明 |
|------|------|
| **UNKNOWN** | 模块未注册或不存在 |
| **REGISTERED** | 已注册但未初始化 |
| **INITIALIZING** | 正在初始化过程中 |
| **READY** | 初始化成功，可正常使用 |
| **ERROR** | 初始化失败 |
| **DISABLED** | 模块被禁用 |

#### 技术优势

| 特性 | 说明 |
|------|------|
| **故障隔离** | 单个模块故障不会导致整个系统崩溃 |
| **状态监控** | 实时掌握所有硬件模块状态 |
| **灵活配置** | 支持必需和可选模块区分 |
| **线程安全** | 多任务环境下安全访问 |
| **可移植性** | 使用标准C类型，易于移植 |
| **调试友好** | 提供详细的状态报告和错误信息 |

#### 使用示例

```c
// 1. 初始化holder
holder_init();

// 2. 注册硬件模块
holder_register_module("st7789", st7789_init_wrapper, true, NULL);
holder_register_module("aht30", aht30_init_wrapper, false, NULL);

// 3. 初始化所有模块
holder_init_all(true);

// 4. 安全使用模块
if (holder_is_module_ready("st7789")) {
    // 模块已初始化，可以安全使用
    st7789_display_data(data);
} else {
    // 模块未就绪，使用备用方案或记录错误
    LOGW(TAG, "ST7789 not ready, using backup display");
}
```

### 5.3 使用Event Bus

#### 5.3.1 定义事件类型

```c
// 在 event_bus_types.h 中添加

// 模块ID (如果新模块)
#define MODULE_ID_MY_MODULE  0x000B

// 事件类型
typedef enum {
    // ... 其他事件 ...
    
    /* 我的模块事件 */
    EVENT_MY_DATA_READY     = (MODULE_ID_MY_MODULE << 16) | 0x0001,
    EVENT_MY_ERROR          = (MODULE_ID_MY_MODULE << 16) | 0x0002,
} event_type_t;

// 事件数据结构
typedef struct {
    int value;
    uint32_t timestamp;
} event_my_data_t;
```

#### 5.3.2 发布事件

```c
#include "event_bus.h"

// 发布带数据的事件
event_my_data_t data = {
    .value = 42,
    .timestamp = xTaskGetTickCount() * portTICK_PERIOD_MS
};
EVENT_BUS_PUBLISH(EVENT_MY_DATA_READY, &data);

// 发布无数据事件
EVENT_BUS_PUBLISH_EMPTY(EVENT_MY_ERROR);
```

#### 5.3.3 订阅事件

```c
#include "event_bus.h"

// 事件处理函数
static int on_my_data(const event_t* event, void* user_data) {
    const event_my_data_t* data = (const event_my_data_t*)event->data;
    LOGI(TAG, "Received data: %d", data->value);
    return 0;
}

// 订阅事件
event_subscription_t* sub = event_bus_subscribe(
    EVENT_MY_DATA_READY,
    on_my_data,
    NULL
);

// 取消订阅
event_bus_unsubscribe(sub);
```

### 5.4 使用Tasker

#### 5.4.1 创建一次性任务

```c
#include "tasker.h"

// 任务回调函数
static enum task_t my_one_shot_fn(void* ctx) {

    return TASK_OK;
}

// 初始化并提交任务
struct task_node node;
tasker_task_init_mi(&node, 0, 1, "one_shot", my_one_shot_fn, NULL);
```

#### 5.4.2 创建周期性任务

```c
#include "tasker.h"

// 周期任务回调
static enum task_t my_periodic_fn(void* ctx) {
    // 周期性执行
    return TASK_OK;
}

// 初始化周期任务 (每1000ms执行一次，无限运行)

tasker_task_init_mi(&node, 1000, -1, "periodic", my_periodic_fn, NULL);
```

## 六、最佳实践

### 6.1 模块设计原则

1. **单一职责**: 每个模块只负责一个功能
2. **接口隔离**: 通过头文件暴露公共API，隐藏实现细节
3. **依赖注入**: 通过事件总线和设备树实现松耦合
4. **错误处理**: 所有API返回错误码，调用者必须处理

### 6.2 事件设计原则

1. **粒度适中**: 事件不要太细粒度，也不要太粗粒度
2. **数据完整**: 事件数据应包含足够信息，避免订阅者再次查询
3. **类型安全**: 使用强类型数据结构，避免void*转换
4. **命名规范**: `EVENT_<MODULE>_<ACTION>`

### 6.3 任务设计原则

1. **快速返回**: 任务函数应尽快返回，避免阻塞调度器
2. **合理周期**: 根据实际需求设置周期，避免过度轮询
3. **错误恢复**: 任务失败时应有恢复机制
4. **资源释放**: 任务取消时释放占用的资源

### 6.4 硬件抽象原则

1. **设备树配置**: 所有硬件参数通过设备树配置
2. **驱动封装**: 硬件操作封装在驱动层
3. **错误传播**: 硬件错误通过事件总线通知上层
4. **资源管理**: 初始化/反初始化配对，避免资源泄漏

## 八、常见问题

### Q1: 事件没有被接收

**可能原因**:
1. 事件总线未初始化
2. 订阅者未注册
3. 事件类型不匹配
4. 队列已满

**排查步骤**:
```c
// 1. 检查事件总线状态
event_bus_print_status();

// 2. 检查订阅者
event_bus_print_subscribers();

// 3. 检查统计信息
uint32_t dropped;
event_bus_get_stats(NULL, NULL, &dropped, NULL);
if (dropped > 0) {
    LOGW(TAG, "Events dropped: %lu", dropped);
}
```

### Q2: 任务未执行

**可能原因**:
1. Tasker未初始化
2. 任务未提交到调度器
3. 队列已满
4. 任务被取消

**排查步骤**:
```c
// 1. 检查队列状态
if (tasker_is_full()) {
    LOGE(TAG, "Task queue is full");
}

// 2. 检查任务返回值
int ret = tasker_enqueue(&node);
if (ret != TASK_OK) {
    LOGE(TAG, "Failed to enqueue task: %d", ret);
}
```

### Q3: 设备树读取失败

**可能原因**:
1. 设备树未初始化
2. JSON配置文件不存在
3. 节点/属性名称错误
4. 类型不匹配

**排查步骤**:
```c
// 1. 检查设备树是否初始化
if (!dtree_is_initialized()) {
    LOGE(TAG, "Device tree not initialized");
}

// 2. 检查节点是否存在
if (!dtree_has_node("my_device.sensor")) {
    LOGE(TAG, "Node not found");
}

// 3. 检查属性是否存在
dtree_node_t* node = dtree_get_node("my_device.sensor");
if (!dtree_has_property(node, "pin")) {
    LOGE(TAG, "Property not found");
}
```
